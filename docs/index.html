What it does

Migrating a site between platforms usually means hand-written scripts, silent data loss, and no way to rehearse. migrateme.tech treats a migration as a pipeline you can inspect: extract, map, rehearse with a full dry-run risk report, approve, execute with checkpoints, then validate with a reconciliation report.

  • First proven path: WordPress (WXR export) → Markdown / MDX, run end-to-end against a real site (see Proof)
  • One core engine, three surfaces: CLI, MCP server, and web
  • AI field mapping with strict output validation — deterministic rules first, AI only where fields get messy
  • Safe by default: dry-run before execution, checkpointed runs with resume, idempotent writes
  • New in Universal: the same canonical model, opened up to every format below — in your browser, with nothing uploaded

Universal: anything to anything

MigrateMe Universal generalises the v1 pipeline into a canonical hub. Every source parses into one shared content model; every destination renders from it. No N×N pair converters — add one parser or one renderer and it composes with everything already there. It runs entirely in your browser: files you open never leave your device.

  • In: WordPress WXR (plus the Squarespace and WordPress.com variants), Markdown / MDX folders, Ghost, RSS / Atom, Blogger, Shopify CSV, Webflow CMS CSV, Notion ZIP, Medium ZIP, Sanity NDJSON, Contentful JSON, Open Migration Package — and a Scanner (lite) that reads a public site’s sitemap, feeds, and structured data when a platform offers no export. It is a best-effort reader, labelled as one — not a crawler, and it never bypasses logins or paywalls
  • Out: Markdown / MDX, WordPress WXR, Ghost, static HTML, RSS / Atom, Blogger, Shopify CSV, Webflow CSV, Sanity NDJSON, Contentful import JSON, canonical JSON, CSV, and the Open Migration Package
  • Honest by construction: every route is labelled Supported, Lossy (with the losses named in the report), or Planned. The registry drives 1,332 pair pages — one for every directed source × destination pair — each stating what a conversion keeps and drops before you run it
  • Accessible: built to WCAG 2.2 AA — full keyboard flow, visible focus, statuses announced as icon plus text (never colour alone), and generated HTML that flags missing alt text

Try Universal live — pick a pair, or start from any pair page. Universal was built in a single Bolt Forge weekend and folded into this repository on October 18, 2026 (PR #35): the connectors live in packages/connectors, the app in apps/web.

The name is the spec

Every address in this project declares what it is. The naming convention is the product idea, worn on the outside:

AddressWhat its name tells you
wp.sandboxThe source: a WordPress site, in the sandbox namespace where testbeds live
wp.spacefast.sandboxThe same WordPress site after a route to SpaceFast — the platform it moved to, named in the address
from.wp.sandboxThe output of this toolkit's run — everything that came from the wp.sandbox source
lovable.sandbox · lovable.cloud.sandboxThe Lovable editions of the testbed — platform, variant, namespace
migrateme.techThe toolkit itself: name the migration, get migrated

The convention scales to routes. A migration pair gets an address in the form source.to.destination — it reads as the migration itself:

lovable.wordpress.migrateme.tech

wordpress.static-html.migrateme.tech

Read the URL and you already know the source, the destination, and the tool. The pair pages behind these addresses already exist — all 1,332 of them, generated from the Universal registry and live in the app today (issue #17); the subdomain rollout that points these addresses at them is the next step.

The standard: Open Migration Package

Universal is the reference implementation of the Open Migration Package (OMP) — an open format any tool can read or write, so content stops being hostage to whichever platform holds it today. A package is a folder (or ZIP) with a verifiable shape:

  • manifest.json — format and version, source platform, every item, asset, taxonomy term, field mapping, and provenance entry
  • content/ — one Markdown / MDX file per item; bodies can also be expressed as Portable Text blocks
  • assets/ — the binaries, indexed; SHA-256 checksums over the package, BagIt-style (RFC 8493), so an importer can prove nothing was altered or dropped silently

The JSON Schema, validator, and full specification live in this repository (packages/format, docs/format), with three conformance levels — OMP Reader, Writer, and Full. The adoption ask: if you build a CMS, a site builder, or an AI app builder, ship OMP import and export. Your users’ content should be able to leave — and arrive — without a rescue mission. The platforms named on this page are the first adoption targets.

Proof, not promises

On October 14, 2026 the toolkit ran against a real WordPress site — not a fixture. The source is DXS, a purpose-built WordPress testbed; its live export went through the full pipeline: plan, dry run, approved migration, validation.

  • 44 items migrated — posts (incl. draft, private, and scheduled), pages, attachments, plus the site's templates, navigation, global styles, and even its AI Guidelines
  • 420 field mappings — 287 deterministic, 133 held for human review rather than guessed
  • 310 risks flagged in the plan; zero files written by the dry run
  • Validation passed: 44 expected, 44 found, empty exception queue

How it's paid for

Freemium, with a donation bundle instead of a paywall. The toolkit is free and MIT-licensed, and the AI step runs a local open-weight model, so a migration costs nothing to run — that's what makes freemium honest here rather than a trial in disguise.

When a migration succeeds, the tool inventories the open-source technology it touched: the platform the site came from, the platform it's going to, and the open-source stack the tool itself stands on. Where a project has an open-source foundation behind it (the WordPress Foundation is the model), the tool assembles a suggested donation across all three directions — source, destination, and the conversion itself. A Humble Bundle–style slider lets you set the amount and choose the split: how much supports this tool, and how much flows to the foundations and libraries that made the original site, the move, and the new site possible.

Designed, not yet wired: the MVP ships the migration pipeline; the donation bundle is the business model it will grow into, because a tool that moves people between open-source platforms should feed the commons it depends on.

Open source, top to bottom

This project is open source standing on open source — and the donation bundle above is priced from exactly this inventory. The tool's job, when it ships, is to detect stacks like these at a migration's source and destination; these are the ones this migration story itself used, at every step:

LayerOpen-source stack
The sourceWordPress (GPL, WordPress Foundation) on PHP and MySQL — and Simply Static (GPL), the plugin that produced the SpaceFast edition's export
The toolkitTypeScript on Node.js; Zod for schema validation, saxes for WXR/XML parsing, better-sqlite3 / SQLite for checkpoint state, the Model Context Protocol SDK for the agent surface, pnpm and Vitest in the toolchain
The AIOllama serving open-weight models locally — the mapping step runs on the user's machine, under the user's choice of model
The formatsMarkdown / MDX, JSON Schema, Portable Text, BagIt (RFC 8493), the Model Context Protocol — and now the Open Migration Package itself, this project’s own contribution to the list. Every interchange format in the pipeline is an open one
UniversalReact and Vite, styled on the open Web Awesome design system — built in a Bolt Forge weekend, then folded into this repo and re-verified locally before merge
The testbedsReact, Vite, Tailwind CSS, shadcn/ui on Radix UI, TanStack Router / Query / Start, React Hook Form, and Supabase on PostgreSQL for the cloud edition
These sitesHand-written HTML/CSS/JS (and the Font Awesome free icons in these headings) on GitHub Pages; the migration-output site is generated with Python, the Markdown library, and Pillow

One honest exception, named rather than hidden: the code was planned and largely written with GitHub Copilot, which is proprietary. Everything it produced, and everything that code runs on, is open.
